# ADR-0008：监督窗口关窗预告与计票前置门——LLM 本地时钟语义

- 状态：已接受
- 日期：2026-08-26
- 关联调研：ADR-0006（监督窗口）同源；现实锚点：立法法 §40③「常委会会议后」的汇总通报义务——先通报、后进入决定
- 影响范围：`src/protocol.ts`（RecordKind+warning）、`src/service.ts`（tally 双门）、`src/tools.ts`（pc_record 新 kind）、`src/client/MeetingStage.tsx`（窗口状态）、smoke/render 测试、SKILL

## 背景

现实里的监督窗口（公示期）是个**长时段**：给监督者留足检查时间，流程合法停顿。LLM 会话**短**且用户不能 24 小时在场——把窗口做出「等待公示期」语义会直接死锁（无墙钟、无缺席者概念）。

必须把「关窗」从瞬时事件改造成**可预示事件**：监督者即使只剩一拍，也知道这一拍存在并被协议保证。

同时，约束力问题：SKILL 是提示词、默认无约束力。若「关窗预告」只写在 SKILL，就是君子协定，会被跳过。「所有可机械化的裁决点下沉为代码强制」是项目立身原则（README 明文），预告的**存在性**必须由服务层强制。

## 决策

引入 **`warning`（关窗预告）记录种类**＋**计票前置门**，并把监督窗口的总时钟语义钉为「LLM 本地时钟」：

1. **时钟语义**：流程的停顿只由协议事件驱动（阶段推进／计票／轮次上限），**没有任何墙钟等待点**；「公示期」的 LLM 等价物＝⭐阶段自然时长＋一轮必发的关窗预告。
2. **门一（WARNING_REQUIRED）**：对 ⭐ 表决阶段计票前，必须先已有该阶段/轮次（stage+round）的 `warning` 记录；否则 `pc_tally` 被拦截。主持人登记 warning 的同一话轮即向用户宣告「拟计票、窗口即将关闭」——这一拍由代码保证存在。
3. **门二（SUPERVISION_PENDING）**：⭐ 表决阶段计票前，该阶段/轮次还须已有 `supervision` 监督记录（本人意见／明示放弃／替身意见皆可）；否则被拦截。这是「用户缺席兜底」的机械出口：主持人必须代录用户回应、或让用户明示放弃、或 spawn 替身（见 ADR-0009）才可计票。
4. **豁免**：门禁只对 ⭐ 阶段生效，且 **MIN 类型豁免**——其 ⭐ confirm 是核验语义的更正循环（ADR-0002 确证书），非征意审议，套门会侵蚀「便宜确证通道」的定位；LEG 公布批准非 ⭐ 亦不在其列。
5. `warning` 记录强制非空通报摘要（拟计票对象），把「先通报内容」也机械化；入审计链，UI 以「关窗预告」种类呈现。

## 后果

- 正向：关窗从瞬时事件变为**可预示**且**机械保证存在**的事件；「用户缺席」不再悬死流程——门禁把主持人困在「必须收束监督窗口」的位点上；监督窗口无需任何墙钟。
- 代价：每次 ⭐ 表决多两拍（预告＋收束）；主持人多两条机械义务（与 RULING_REQUIRED 同族）；一个新增 RecordKind。
