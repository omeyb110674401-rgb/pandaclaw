# ADR-0010：复审回告闭环——归档后效力的纠错与回告

- 状态：已接受
- 日期：2026-08-26
- 关联调研：A-补-P17《备案审查流程实质化》（登记→审查→纠错→反馈闭环）、D-补-P112《公开建言的意见量级与反馈闭环》统一结论；现实锚点：监督法第五章 §38–45、立法法 §113（向审查建议人反馈）、«法规、司法解释备案审查工作办法»
- 影响范围：`src/protocol.ts`（RecordKind +review/review-reply、复审状态机常量）、`src/service.ts`（复审流程服务方法、待审池、tally 门二改造）、`src/index.ts`（服务层 spawn 机制）、新 preset `pc-reviewer`（审查替身）、`src/tools.ts`（复审工具面）、`src/client/MeetingStage.tsx`（复审窗口/待审池）、测试、SKILL

## 背景

ADR-0006 与 ADR-0009 把监督窗口建成闭环的「入口」（会中主窗＋归档后复审子通道），但复审子通道只以 UI 复制开场白存在，**没有数据面**：归档后会议只读（`NOT_OPEN` 禁一切记录）、`RecordKind` 无 review 类型、主持人无复审落板工具。监督闭环的出口是空的——意见提了、窗口关了、开场白复制出去了，然后呢？

现实制度提供了完整的复审模板（备案审查，监督法 §38–45）：登记（有件必备）→受理分办（审查建议通道）→审查（主动/被动/专项）→沟通纠正（与制定机关协商，自纠优先）→决议出口（撤销/修改废止/法律解释三出口，唯一开会处）→反馈公开（向提出人回执处置结果，立法法 §113；年度报告，监督法 §45）。

## 决策

### 1. 复审是原案卷的效力处置模型（Q4-D）

复审不产生独立审查卷、不复活原案卷：复审意见落**原案卷**内 `review` 记录（归档后唯一写入面）；六阶段状态机在**原案卷的复审子状态**上推进；`status` 保持 `adjourned` 不回到 open——原决议永远留在已归档状态，复审在效力层处置它。开会只发生在出口的「修订/解释」分支。

### 2. 完整六阶段状态机（Q3 现实校准）

| 阶段 | 现实同构（A-补-P17） | 系统承载 | 推进者 |
|---|---|---|---|
| ① 登记 | 有件必备 | `review` 记录落板 | 用户/服务层（自动） |
| ② 受理分办 | 工作机构先行 | 服务层检查（有效/重复/范围） | 服务层（自动） |
| ③ 审查 | 机关式审查（不开会） | 审查替身出「审查意见＋逐条处置清单」 | 服务层 spawn，自动 |
| ④ 沟通纠正 | 与制定机关协商，自纠优先 | 审查意见呈报前异议方陈述（被动） | 服务层唤醒，自动 |
| ⑤ 决议出口 | 唯一开会处（三出口） | **用户门上三选**：修订重议／解释性决议／驳回并说明 | 用户（真人裁量） |
| ⑥ 反馈公开 | 向建议人回执 | `review-reply` 逐条回告 | 服务层（自动） |

### 3. 案卷级流程＋逐条回执（Q5-C）

六阶段状态机是**案卷级一个**（复审针对决议整体）；「处置清单」与「回告」**字段级分条**——每条 `review` 记录关联自己的处置结论与回告文本，满足「凡触发复审的建议，必须向建议人回执处置结果」（D-补-P112 统一结论）。UI 每条意见可追踪自己的处置状态。

### 4. 审查替身：服务层全自动 spawn（Q6/Q7 策略一）

审查主体**不是主持人**（主持人读记录流可能被污染，spawn 参数由其生成即污染传导）。审查替身由服务层直接 `ctx.agents.create()`：`seed` 为空、`setup` 提示词与工具面代码硬编码——**用户输入一个字都不进 spawn 参数**。替身产物经专用工具直写服务层（同 `superviseStandin` 模式），不经主持人 `pc_record` 代录。

### 5. 结构化审查包（Q9-B）

审查替身不读案卷记录流（不可信任意文本）：服务层在 spawn 前构造**结构化审查包**——案卷号、议题、会议类型、阶段完成情况、决议原文、票况统计、规约核对结果——只经 setup 注入这些代码选取的结构化数据。用户意见/监督意见原始全文零进入替身高文。

### 6. 异议方成员原会话续接（Q12-A/Q13-B）

归档时**不解散异议方子代理**（改 `team_dismiss` 语义）；复审已触发时唤醒其**原会话**（带会中记忆与身份），以**被动陈述人**身份向审查环节陈述原异议论据（为什么这个决议有问题、当初的质询为什么成立）。它不主动开路（无新信息源），不参与裁量（利害关系人不裁判自己的案子）；出口永远用户裁定。

### 7. 入口：用户主动＋有备必审分层（Q14/Q15/Q17-B）

复审入口两个来源，均为零 AI 判断：
- **用户主动**：用户发现问题提 `review` 记录（被动，ADR-0006 既有语义）；
- **有备必审分层**：所有归档案卷进入**待复审池**（备案必审的登记语义），出审按**类型效力分层**——复审审的是「决定对不对」，效力等级决定复审必要性与出审次序：

| 档位 | 会议类型 | 出审策略 |
|---|---|---|
| 主力档 | RES 决议型、LEG 立法型 | 入池即自动出审；降级态（征询采信·未达法定状态/验收 skip）**优先**；备案审查直接同构（D-补-P112：RES「归档后常设复审通道」） |
| 次级档 | PLA 规划型、STR 战略型 | 轮候；仅用户提意见或指定专项时触发 |
| 弱档 | CON 协商型 | 仅用户提意见时触发（共识非规范，效力弱） |
| 不入池 | MIN 纪要型 | 不产生新决定（「记」非「决」），无复审对象；对纪要内容的异议走会内更正循环，不进归档后复审 |

用户可随时指定专项（「专项审这批」）。机械可检的协议违规不进复审——那应在归档门禁拦截。复审只处理**机械门禁检不到的东西**（决议质量/正确性）与**协议盖章放行但留了尾巴**的降级态。

### 8. 出口落地（Q10-A/Q16）

审查替身出**建议性审查意见**（维持/建议修订/建议解释/建议驳回＋逐条理由）→ 呈用户 → 用户以门上裁量者帽子三选：
- **修订重议 → 新案卷关联原卷**：convene 同类型新会议（新文号），决议落新卷；原卷记录流追加处置标记「已由 PC-XXX 号修订」——原决议裁决效力被新决议取代，原卷保持归档不复活；
- **解释性决议 → 原案卷追加 `resolution`**（标注「解释性决议」）：解释非修改，是对原决议的权威说明，效力与原文件同级；
- **驳回并说明 → 原案卷追加 `review-reply` 回告记录**：逐条回告每条意见的处置结论与理由。

三选均不触动原案卷归档状态，处置通过记录流表达。

### 9. 监督替身改造（Q8-B，与审查替身同策略）

ADR-0009「主持人经底座 spawn 监督替身」废止：监督替身改由服务层在 **tally 门二受阻时自动 spawn**（计票位点兜底）——主持人调 `pc_tally`，服务层检测「有 warning、无 supervision 记录、门二挡路」→ 当场自动 spawn 监督替身（setup 硬编码）→ 替身异步直写意见 → 再次 tally 放行。触发位点完全确定、无 AI 判断；替身只在计票尝试发生且用户缺席时介入，用户正常回应时永远不会被抢答（本人优先原则）。

## 后果

- 正向：复审从 UI 玩具变成完整纠错闭环（入口→审查→出口→回告全链路）；「去 AI 中介」落地为机制事实（spawn/落板/审查包/分层全部代码机械，零 AI 判断环节）；用户保持唯一真人裁量点（出口三选）；异议方续接补充利害关系人视角，识别问题的主体不再只有用户；监督替身与审查替身共用同一套服务层 spawn 机制。
- 代价：RecordKind 扩展（review/review-reply）；一个审查替身 preset（`pc-reviewer`）；服务层 spawn 机制（`ctx.agents.create`＋setup 硬编码）；三张新状态面（复审子状态/待审池/监督替身自动派发）；`team_dismiss` 语义改为「异议方保留、其余解散」；监督替身派发链路从主持人迁移到服务层。

## 后续

- 待复审池的 UI 呈现（队列/优先级/出审时间）；用户指定专项审查的交互；逐条回告的追踪视图（每条意见的处置状态）；解释性决议的文种样式；「有备必审」的轮候节律（协议事件驱动，不读墙钟——LLM 本地时钟语义延续）。

## 执行模型细化（2026-08-26 追加裁定：Q1′–Q5）

初版第 7 节「入池即自动出审」在执行层发现落差（手动 dispatch 才推进、降级标记含误标），经第二轮拷问细化如下：

1. **归档位点批量泵（Q3-B）**：主力档归档即入池（filed），归档事件内服务层把池中全部主力档按 `priority` 排序**逐个 spawn** 审查替身（串行）——「自动出审」由归档事件保证，无需人工 dispatch；泵只处理主力档，用户在场档留在池中。
2. **复审模式分层（Q2）**：主力档（RES/LEG）＝**自动复审档**（泵出审，跑到 decidable 停等用户三选）；次级/弱档（PLA/STR/CON）＝**用户在场复审档**（归档只登记，用户 `request`/`dispatch docIds` 专项开启）；MIN 不入池。复审是用户参与的主要入口之一，手动窗口必须完整保留。
3. **降级标记修正（Q4）**：降级态唯一＝`consultive`（征询采信）；`skip-validation` 不再是降级态（RES 默认 skip 是正常产物，非「留尾巴」，其检验由自动复审覆盖）——类型保留兼容旧数据，不再产出。降级标记转审查语义：注入结构化审查包，替身重点核验征询采信是否合理。
4. **专项出审（Q1″）**：`reviewDispatch` 从「按优先级取号」改为「`docIds` 指定批次」（用户明确点名要审的档案，可含任意档位）——主力档已由泵自动出审，专项是手动窗口的批量形态。
5. **分级批量驳回（Q5-A）**：审查意见为「建议维持/建议驳回」的多件 decidable 档案可一键 `batch-dismiss`（统一注）；「建议修订/建议解释」必须逐件三选（实质变更不批量化）。

## 效力语义修正（2026-08-27 追加裁定：Q13–Q19）

第三轮拷问后，出口效力链路与归档门禁的语义修正如下（执行层韧性 Q1–Q12 见 ADR-0011）：

1. **修订新卷正常入池（Q13-A）**：修订重议产出的新卷归档后**按档位正常进入待复审池**（主力档自动泵、弱/次级档用户在场），**无循环豁免**——复审链终止条件＝用户三选 dismiss / 逐条回告闭环，不是次数上限。修订不重置审查义务，改完再审、审完再改是协议事实，终止权永远在用户。
2. **修订谱系双向入档＋审查包增强（Q14-A）**：`reviewLinkLanding` 对称关联——原卷记 `revisedDocId`（已有），新卷记「修订来源」（`originDocId` ＋ 上轮审查结论摘要）；新卷出审时 `buildReviewPackage` 注入「修订来源与上轮审查结论」，审查焦点＝**修订是否消除原审查意见指出的问题**。谱系与核验焦点一体化，审计对称。
3. **解释性决议同效力同义务（Q15-A）**：解释性 `resolution` 落板后同卷复审状态机**再开一轮**（count 累计，MAX_REVIEW_PER_DOC 上限仍在）；审查包注入「此前已有解释性决议，核验解释是否与原决议冲突/引入新问题」。解释不是免审金牌（现实同构：法规解释同法规效力、同样报备），「效力同级 → 义务同级」对称。
4. **归档门禁程序/实体分工（Q16-A/17-A/18-A）**：归档门禁管**程序合法性**（决定怎么作出的）、复审管**实体正确性**（决定对不对）。补全清单：决议锚点存在（红线 8）、阶段全部完成（已有）、**表决合法性**（该档表决阶段 VOTE_STAGES 唯一元素至少一条 tally 记录——「决定必经表决」红线引擎化，无 tally 的决议归档 `ADJOURN_BLOCKED`）。验收门维持 ADR-0005「引擎零门禁」行为规约（三选由既有原语承载，不造新门禁）。
5. **审查意见三分类收敛（Q19-A）**：审查替身意见收敛为**维持／建议修订／建议解释**——「建议驳回」不再产出。理由：替身「建议驳回」（备案审查同构＝建议撤销原决议）与用户出口「驳回并说明」（既定语义＝驳回审查建议、维持原决议）**方向相反**，同词异义且批量驳回会把「建议撤销」一键「维持」——方向性错误。撤销作为修订子形态（现实：废止常以「修改废止」文件承载）经重议产出；batch-dismiss 分流改为**仅「维持」可批量**，「修订/解释」逐件三选。

## 后续（效力）

- 修订新卷的谱系字段在客户端呈现（新卷标识「修订自 PC-XXX」）；解释性决议的再开轮在复审窗口可见；
- 归档门禁的 tally 检查对 MIN（确证 tally）与 LEG（publish 计票）同样适用——各档表决阶段恒有 tally 义务。
