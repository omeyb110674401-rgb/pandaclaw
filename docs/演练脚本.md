# PandaClaw 实战演练脚本

> 用途：DSH 重启后按本脚本逐场执行，每场结束对照「预期结果」栏勾验。任何不符即协议实现缺陷，记入迭代清单。
> 前置：`team_*` 八件套可用；maxTeammates=12 已生效；pandaclaw-meeting v2.1 技能已采纳。

## 演练一：纪要型最小闭环（验证目标：建会/板书规范/轻量确认/存档）

- 配置：MINUTES / simple（cppcc 2 + npc 1）/ skip 验收
- 建议议题：「PandaClaw 项目周会纪要：协议 v2.1 的演练安排」

### 执行要点
1. P1 议题包写入 `agenda`，文号 `PC-MIN〔当年〕{序号}号`
2. P2 组队：cppcc-1（DevOps 专家）、cppcc-2（项目经理）、npc-1（风险评估师），全 managed
3. §5 三段座谈式轻量回路：介绍 → 预约式发言（按《意见书》格式 ≤300 字；即席补充每人限一次 ≤200 字）→ 归纳确认
4. 文档生成 `.pandaclaw/{文号}.md` 后 team_dismiss

> 发言参数依据：双周协商座谈会现实校准（D-补-P112，两独立来源互证）——预约发言 5 人×8 分钟≈300 字、即席每人 5 分钟≈200 字。原「各 60 字内」为设计错误，已修正。

### 预期检查点
- [ ] 成员无横向消息（team_list 流量里 to 只出现 leader）
- [ ] 板书仅出现：agenda / opinion-minutes-cppcc-{1,2} / draft-minutes / resolution 类归档键
- [ ] 纪要免表决：全程无 vote-* 键
- [ ] 文档元信息块含成文日期与文号；内容可溯源到板书
- [ ] 全程回合数 ≤ 用户回合 6 个（控费观察）

## 演练二：协商型完整回路（验证目标：R0-R4 全机制）

- 配置：CONSULTATION / medium（cppcc 3 + npc 2）/ key 验收
- 建议议题：「团队代码评审流程的改进方案」（有真实分歧空间，能自然产生质询与反对票）
- 身份建议：cppcc = 架构师 / DevOps 专家 / 测试专家；npc = 可行性评估师 + 合规审计员

### 执行要点
1. 大流程六阶段各建 task；起草阶段开回路（R0-R3），审议阶段开回路（R0-R4+验收门暂停）
2. R1 准入审查必须实际执行一次退回（可指示某 cppcc 第一版只写立场不给建议，触发负面清单第②条）
3. R4 至少构造一次「打回」：提前告知 npc-1 从可行性角度保留反对意见（验证重议与焦点提炼）
4. 第二轮通过后触发 KEY 验收门，向用户展示决议记录摘要并等待放行
5. 征求意见阶段验证 M9 完整性语义：意见处置清单逐条列采纳/不采纳及理由

### 预期检查点
- [ ] 退回重提发生且附理由，未静默丢弃
- [ ] 表决前置门：vote-* 出现前同 stage 存在 opinion-* 与 inquiry-*
- [ ] 打回后第二轮总轮次=2（≤3 上限内）；反对焦点被准确提炼为新一轮 R0 输入
- [ ] 计票与下方用例表一致；resolution-* 含成文日期
- [ ] 验收门真的停下等待用户输入
- [ ] 最终文档章节齐全，处置清单在附录

## 附：计票用例表（v2.1 公式机械验证）

公式：普通=`赞成 > 全体npc÷2`；重大事项(full 终批)=`赞成 ≥ 全体npc×2/3`；弃权计入分母不计入分子。

| 场景 | npc 数 | 票型 | 普通 | 重大事项 |
|---|---|---|---|---|
| 过半 | 3 | 2赞1反 | ✅通过(2>1.5) | ❌(2<4) |
| 弃权拖累 | 3 | 2赞1弃 | ✅通过 | ❌ |
| 平票算术 | 3 | 1赞1反1弃 | ❌打回(1≯1.5) | ❌ |
| 全弃权 | 3 | 3弃 | ❌打回 | ❌ |
| 反对占优 | 3 | 1赞2反 | ❌打回 | ❌ |
| 压倒 | 5 | 4赞1反 | ✅(4>2.5) | ✅(4≥3.34) |
| 临界不足 | 5 | 3赞2反 | ✅(3>2.5) | ❌(3<3.34) |

启动门槛：应答<2/3 不付表决（medium=2 人应答起）；simple 单 npc 必须应答。
边界说明：simple 档单人 npc 时「过半数」实为一票定音（形式审查性质）——重要决策应使用 medium 及以上，此局限写入文档模板的「效力说明」节。

## 迭代记录

### 演练一 · MINUTES 变体C（2026-08-26）——五项全绿 ✅

- 结果：agenda → opinion×3（含 M4 退回重提一次，`-r0` 留痕）→ draft-minutes → resolution-minutes-confirm → 文档 `PC-MIN〔2026〕001号.md` 成文。3 次 workflow 单发、7 个 agent 委托。
- 五项检查点全部 pass（阶段完整/字数准入/原样转写/溯源完整/文档规范）。
- **架构发现（进迭代清单）**：
  1. 子代理永不成为领导：dsh-team `leads()` 门禁 `origin !== 'subagent'`，团队工具不进入子代理作用域；
  2. headless 单发模式在主持人结束回合时即退出——回合驱动屏障无法在无人值守单发下工作；
  3. 原生 subagent 工具在 headless 为 continuable 后台模式；阻塞式成员交互须用 workflow 工具（前台同步）；
  4. Windows 下 `job_kill` 不级联杀子进程；按命令行匹配清扫会误伤同型进程。
- **协议偏离（变体C 固有，留待 GUI 常驻会话补验）**：无 team_spawn/mailbox 往返/冷恢复验证；板书由主持人代录；R0 卡并入 agenda。
- 亮点：M4 准入审查被主持人自发正确执行（npc 首稿 344 字超限→退回→295 字重提，`-r0` 留痕），红线 6 同时生效。

### 演练二 · CONSULTATION 变体C（2026-08-26）——六项全绿 ✅

- 结果：R0 出题 → R1 三份意见＋准入 → R2 质询×2＋答辩 → R3 草案v2＋处置清单 → R4 第一轮表决 **0赞/2反＝打回**（焦点 F1可行性/F2合规 提炼入 `issue-drafting-focus`）→ 焦点修订 → 第二轮 **2赞/0反＝通过** → `resolution-drafting` 归档 → 公文 `PC-CON〔2026〕001号.md` 成文。总轮次 2/≤3。6 次 workflow 单发、21 键板书。
- 六项检查点全部 pass；计票与用例表一致（基数=全员编制，赞成>1）；npc-2 未受编排自主投反对，首轮必然打回——机械结果稳健。
- **演练暴露缺陷（已修）**：裸 `agenda` 键跨会议碰撞（三场会议互相覆盖风险）→ v2.4 引入会议作用域键。
- **协议张力记档**：M4「退回重提」与「原样转录」指令在变体C 下冲突（D3：三份意见书均超300字被直接转录）→ v2.4 明确准入审查先于转录；D4 选票理由两次超80字→明确字限为行为规约而非计票效力条件；D5 M13 快确认被正式表决覆盖省略。

### v2.4 迭代裁决（基于两场实测）

| # | 裁决 | 来源 |
|---|---|---|
| V1 | **板书键加会议作用域**：`agenda-{文号}` / `issue-{文号}-{stageid}` 等，杜绝跨会覆盖 | 演练二实撞 |
| V2 | **准入审查时点前移**：任何来源的意见书先过 M4 再上板；变体下超限即退回，不得以「原样转录」豁免 | 演练一正例/演练二反例 |
| V3 | **字数上限定性**：发言/理由字限为行为规约，违反记档但不影响选票与决议效力（效力只看红线2/3） | 演练二 D4 |
| V4 | **无人值守运行形态**：单发环境用 workflow 同步原语替代回合屏障；回合驱动屏障/邮箱往返/冷恢复仅在常驻会话成立，协议标注适用前提 | 架构发现 1-4 |
| C1-C9 | C9 全链状态机校验采纳为红线2扩展（演练二 21 键序列即合法迁移实例）；C7 匿名表决、C8 版本化文本、C3 发起权独立等留待「修协议自身」场景启用时再裁 | 两场演练未触及宪章级场景 |
