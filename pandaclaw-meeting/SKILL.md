# PandaClaw v2.4 — 民主协商会议协议（dsh-team 底座 · 实测校准版）

主持人 = 当前主会话（team leader）。政协委员（cppcc-N）提方案，人大代表（npc-N）审方案并表决。一切交流经主持人，成员之间禁止横向发消息。

**依据链**：本仓库 `docs/` 目录（在线阅读：https://github.com/omeyb110674401-rgb/pandaclaw ）——`docs/协议校准底稿.md` 含 M1-M17 制度裁决，`docs/research/` 为三轮现实制度调研产出（54 份），`docs/演练脚本.md` 记录两场实测。核心边界：协商者无决定权、决定必经表决；主持人对应「统一审议＋委员长会议」的中立枢纽——主导合议但不提案、不投票。

前置：dsh-team 已安装且 `team_*` 工具可用。enterprise 档需 profile 配置 `maxTeammates: 12` 以上。

**运行形态前提（v2.4 实测新增）**：
- **常驻会话**（GUI/交互）：完整协议可用，回合驱动屏障＝主持人结束回合等待邮箱投递唤醒。
- **无人值守单发**（headless 等）：回合结束即退出，屏障失效——成员交互改用 workflow 工具前台同步委托（并行 agent()），产物由主持人代录上板并标注「代录」。
- 团队工具仅存在于普通会话作用域；子代理（origin=subagent）永远无法担任主持人。

## 1. 会议类型矩阵

先和用户确定：会议类型、议题、成功标准、约束。未指定则按"适用场景"推荐。

| 类型 | 代号 | 阶段流（⭐=开协商回路，其余主持人直办） | 默认验收 | 适用 |
|---|---|---|---|---|
| 纪要型 | MIN | 记录 → 整理 → ⭐确认(轻量) → 存档 | skip | 例会留痕、快速共识 |
| 决议型 | RES | 立项 → 起草 → ⭐审议 → 公布 | skip | 快速拍板 |
| 协商型 | CON | 立项 → 调研(通报) → 起草(⭐R1-R3) → 征求意见(⭐全程) → ⭐审议 → 发布 | key | 重大议题系统方案 |
| 规划型 | PLA | 评估 → 研究(⭐) → 编制 → 意见征求(⭐) → 衔接与论证闸门(直办) → 专委会预审(直办) → ⭐批准 → 发布 | key | 中长期规划 |
| 战略型 | STR | 评估 → 研究(⭐) → 规划起草(协调确认) → 意见征求(⭐) → ⭐内圈审议(可打回) → ⭐外圈终审批准 | full | 顶层战略部署 |
| 立法型 | LEG | 立项 → 起草 → 公开征意(⭐) → 专家论证(⭐) → 合规审查(⭐可打回) → ⭐合议审议 → 公布 → 备案归档 → 复审子通道 | full | 制度/规范/标准 |

阶段附注：PLA 批准须过衔接硬闸门（下位服从上位、专项服从总体）；STR 区分两条审批链（常委会终审 vs 政治局全体）；LEG ⭐合议审议采用三形态决定（原则通过／退回修改附意见清单／暂不讨论），不走计票，计票仅用于最终公布批准环节。

## 2. 双维度配置

人数（complexity）：simple=cppcc 2+npc 1；medium=3+2；complex=4+3；enterprise=5+5。

验收门（validation）：full＝每次 R4 后暂停请示＋终批启用重大事项规则（门槛 2/3）；key＝仅关键阶段后暂停；skip＝全程自主。PLA 另按年度评价（过程性）/五年考核（终局性）双层节奏；数据造假直接不合格。

## 3. 建会（P 阶段）

P1 议题包：`team_note` key=`agenda-{文号}`（**会议作用域键，v2.4 起强制**）：议题一句话（注明来源类别：用户指定／调研发现／成员动议，遵循小切口原则）、背景与期望结果、成功标准（编号列表，规划型标注约束性/预期性属性）、约束、类型代号与阶段表、三分时点（会前送达/会中讨论/会后报送时限）。文号按 `research/C-补-P12` 代字规则：`PC-{类型字}〔年份〕{序号}号`。

P2 组队（全部 `relation: managed`）：cppcc-i 绑定 §6 提案视角 persona；npc-j 绑定刚性审查定位 persona。persona 模板强制行为规约：

`你是{身份名}，专长{领域}。规约：只回应主持人点名的问题；结论先行，观点必须给理由；意见书≤300字、质询≤100字、选票理由≤80字（字限为行为规约，超限记档不改变效力判定）；禁止纯程序性发言与寒暄；允许对他方观点质疑交锋，由主持人裁判；对程序疑问用询问通道（≤50字短问）；产物以 team_note 写入指定 key 后 team_send 通知主持人一句。`

P3 任务板：每个大流程阶段建 `team_task`；当前置 active，完成置 done 并把决议要点写进 note（一文一事）。

## 4. 协商回路（⭐阶段的执行单元；同一议题总轮次≤3）

### R0 出题（主持人）
`team_note` key=`issue-{文号}-{stageid}`：背景输入、要回答的问题、《意见书》格式与准入标准、产出时限。然后 `team_send` 点名全体 cppcc。

### R1 独立陈述（cppcc）
各成员把《意见书》写入 `opinion-{文号}-{stageid}-{name}` 并通知主持人。主持人结束回合等待投递唤醒（回合驱动屏障，仅限常驻会话；单发环境见运行形态前提）。

**准入审查（M4，先于转录上板）**：①一事一案；②有情况、有分析、有具体建议；③重复者并案标注；④超出议题范围者转出另立；⑤超字数上限者退回重提。不合格的**退回修改重提**（附理由），原稿留痕不删除，不得静默丢弃。
收集判定：全员到齐进 R2；超时追点一次；仍缺且已收 ≥2/3 继续（缺席记档），<2/3 报告用户请示。

### R2 交叉质询与询问（npc ⇄ cppcc）
主持人汇总意见书写入 `issue-{文号}-{stageid}-digest`，点名全体 npc 各提至少 1 个书面质询（`inquiry-{文号}-{stageid}-{name}`），可要求限期答复。质询转发相关 cppcc，**限 1 回合内答辩**（`reply-{文号}-{stageid}-{name}`），超时催办一次；提案方不满意可触发一次二次答辩（有意收紧：现实无重办次数上限；程序原型=上海办法）。未被点名的成员无答辩义务。
**询问通道（M17）**：任何成员可随时向主持人发 ≤50 字短问，不占质询名额、不进计票程序。

### R3 合议修订（主持人主导）
综合意见书、质询、答辩形成《草案 v2》写入 `draft-{文号}-{stageid}`。**双联交付**：修订文本＋《意见处置清单》成对产出——逐条记录来源、经研究摘要、处置结果四分类（采纳/部分采纳/存疑留办/不采纳）及理由，全部处置完毕方可定稿。实质性修改后回传原提案方一轮快确认。主持人保持中立合议，不表态站队、不参与 R4 投票（M11）。

### R4 表决归档（npc）
**启动门槛**：npc 应答率 ≥2/3 方可付表决；simple 档仅 1 名 npc 时必须应答。不足先催办，仍不足降级为**征询模式**（结果仅供参考，标注未达法定状态）。
点名投票：《选票》写入 `vote-{文号}-{stageid}-{name}`，格式 `【投票】赞成|反对|弃权 / 【理由】≤80字`。

**计票公式（M1）**：
- 通过 = `赞成 > 全体npc数 ÷ 2`（基数=全员编制；弃权计入分母不计入分子，算术上等同反对）；
- full 类型最终批准阶段：通过 = `赞成 ≥ 全体npc数 × 2/3`；
- 打回 = 不达门槛：提取反对理由中的质询焦点写入 `issue-{文号}-{stageid}-focus` 回 R1 重议。同一议题总轮次≤3；
- 快速通道：R2 后无实质分歧可直接提前付表决；
- 终止条款：议题搁置跨两个会议周期未推进 → 自动归档终止并通知用户；
- 结果写入 `resolution-{文号}-{stageid}`（票数明细＋每位代表理由＋成文日期=R4 通过日），对应 task 置 done。

**LEG 特例**：⭐合议审议阶段按三形态决定，npc 以合规审查人身份参加合议但不计票；最终公布的批准环节才走 R4 计票。

### 验收门
按 §2 validation 在 R4 后决定是否暂停请示。展示：阶段名、决议、票数、异议要点、下一步计划。

## 5. simple 档座谈式轻量回路（M5，参数经现实校准）

不开完整 R0-R4，改三段（原型：双周协商座谈会）：①情况介绍（主持人写议题卡）→ ②预约式发言（每人 1 次，按《意见书》格式 ≤300 字；即席补充每人限一次 ≤200 字）→ ③归纳确认（主持人归纳总结并宣布，成员 ≤60 字确认或更正，无异议即过；会后 3 日内成文报送归档，批示回流记档）。涉对立立场议题时，预约名额强制分配给不同立场成员。

## 6. 身份库

npc 审查视角（每场至少覆盖可行性 + 风险/合规；定位=刚性审查）：npc-feasible 可行性评估师 / npc-risk 风险评估师 / npc-compliance 合规审计员 / npc-quality 质量监督员 / npc-perf 性能评估师 / npc-global 全局一致性代表。

cppcc 提案视角（按议题领域挑 2-5 个互补专业；定位=协商式监督与参政议政）：
架构/技术：系统架构师、软件架构师、数据架构师、AI 工程专家｜产品/商业：产品策略师、增长专家、商业模式分析师、用户研究员｜工程/交付：DevOps 专家、后端专家、前端专家、测试专家、项目经理｜数据/安全：数据分析师、安全工程师、隐私合规师｜运营/成本：运营专家、成本控制师、供应链专家、法务顾问｜内容/市场：内容策略师、市场分析师。

选题启发：议题关键词命中领域 → 该领域至少 1 名 cppcc + 对应审查视角 npc 必在场。

## 7. 文档生成

元信息块：文号、类型、议题、复杂度、参会名单（列身份名）、成文日期（=最终通过日）、验收模式。骨架按各类型章节执行（MINUTES 含批示回流占位；CONSULTATION 附录含处置清单；PLANNING 含指标分解单与预审意见；LEGISLATIVE 含备案登记）。规则：内容一律取自板书结构化记录，禁止编造；附录列全部 board key 索引；重大事项决议以公告体发布；对既有决议的解释用「解释性决议」附录归档。文档写入工作区 `.pandaclaw/{文号}.md`。公文版式参数见仓库 `templates/layout-gbt9704.yaml`（GB/T 9704 红头版式）。

## 8. 红线

1. 成员一律 managed；出现横向消息立即纠正并记档。
2. **表决前置门＋全链顺序**：`vote-*` 前必须已存在同 stage 的 `opinion-*` 与 `inquiry-*`；整个回路的最小文书序列（议程→意见→质询→答辩→草案→选票→决议）构成合法迁移链，跳步即程序违规。
3. 计票只认 `vote-*` 板书【投票】行；聊天散句不算票；字数超限记档但不影响选票效力。
4. 成员不得自行宣布结论；结论只能出自主持人归档的 `resolution-*`。
5. 一事一案、一文一事。
6. 全程不删除板书（审计链）；错误记录用新 key 覆盖并注明。
7. 主持人在合议与表决中保持中立，不提案、不投票。
8. 解散团队前必须完成文档生成与存档。
