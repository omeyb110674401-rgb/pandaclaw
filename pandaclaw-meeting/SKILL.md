# PandaClaw v2.9 — 民主协商会议协议（dsh-team 底座 · 拷问校准版）

## 0. 使用地图——不读协议也能开会

**主流程**：一句话议题 → 选类型 → 开会 → 收公文。直接对助手说「**开个会：〈议题〉**」即可，未指定类型时按下表推荐；想指定就说「开个协商型会议讨论 X，验收档 key」。

| 你的处境 | 走哪类 | 会中被打扰几次 | 散会拿到什么 |
|---|---|---|---|
| 例会留痕、快速共识 | 纪要型 MIN | ≈0 次（自动确证） | 确证纪要 |
| 方案明确快速拍板 | 决议型 RES | 默认 0 次（skip 档） | 决议 |
| 重大议题系统方案、存在争议 | 协商型 CON | 关键阶段 1–2 次 | 决议＋意见处置清单 |
| 中长期规划编制 | 规划型 PLA | 关键阶段请示 | 纲要（预期性/约束性分列） |
| 顶层战略部署 | 战略型 STR | 内圈裁定＋终审一致同意门 | 战略决议 |
| 制度/规范/标准制定 | 立法型 LEG | 公示期＋逐条反馈 | 条文＋备案记录 |

**三条铁律替你把关**：①结论必经成员表决——你的意见再大也不能直写进决议，只能放行／附意见打回／终止（ADR-0005）；②只有机器谈不拢时才来找你——应答率不足的征询呈报三选、full/key 档的验收门（ADR-0004）；③你随时可以以监督者身份提质疑——会中代录入板（原汁原味不改写），会后走复审（ADR-0006）。

**打扰控制**：验收档 full／key／skip 决定找你的频率，建会时说一声即可指定。

主持人 = 当前主会话（team leader）。政协委员（cppcc-N）提方案，人大代表（npc-N）审查并表决。一切交流经主持人，成员之间禁止横向发消息。

**依据链**：本仓库 `docs/` 目录（在线阅读：https://github.com/omeyb110674401-rgb/pandaclaw ）——领域术语见 `CONTEXT.md`，裁定沿革见 `docs/adr/0001-0006`；`docs/协议校准底稿.md` 含 M1-M17 制度裁决，`docs/research/` 为现实制度调研产出（57 卡），`docs/演练脚本.md` 记录两场实测。核心边界：协商者无决定权、决定必经表决；主持人对应「统一审议＋委员长会议」的中立枢纽——主导合议但不提案、不投票。

前置：dsh-team 已安装且 `team_*` 工具可用；安装 dsh-pandaclaw 插件后本协议的裁决点由代码强制（机械计票/前置门/状态机），未装插件时退化为纯指引。enterprise 档需 profile 配置 `maxTeammates: 12` 以上。

**运行形态前提（v2.4 起）**：
- **常驻会话**（GUI/交互）：完整协议可用，回合驱动屏障＝主持人结束回合等待邮箱投递唤醒。
- **无人值守单发**（headless 等）：回合结束即退出，屏障失效——成员交互改用 workflow 工具前台同步委托（并行 agent()），产物由主持人代录上板并标注「代录」。
- 团队工具仅存在于普通会话作用域；子代理（origin=subagent）永远无法担任主持人。

## 1. 会议类型矩阵

先和用户确定：会议类型、议题、成功标准、约束。未指定则按"适用场景"推荐。

| 类型 | 代号 | 阶段流（⭐=开协商回路，其余主持人直办） | 默认验收 | 适用 |
|---|---|---|---|---|
| 纪要型 | MIN | 记录 → 整理 → ⭐确认(确证书) → 存档 | skip | 例会留痕、快速共识 |
| 决议型 | RES | 立项 → 起草 → ⭐审议 → 公布 | skip | 快速拍板 |
| 协商型 | CON | 立项 → 调研(通报) → 起草(⭐R1-R3) → 征求意见(⭐全程) → ⭐审议 → 发布 | key | 重大议题系统方案 |
| 规划型 | PLA | 评估 → 研究(⭐) → 编制 → 意见征求(⭐) → 衔接与论证闸门(直办) → 专委会预审(直办) → ⭐批准 → 发布 | key | 中长期规划 |
| 战略型 | STR | 评估 → 研究(⭐) → 规划起草(协调确认) → 意见征求(⭐) → ⭐内圈审议(三形态裁定) → ⭐外圈终审批准(一致同意) | full | 顶层战略部署 |
| 立法型 | LEG | 立项 → 起草 → 公开征意(⭐) → 专家论证(⭐) → 合规审查(⭐可打回) → ⭐合议审议(三形态) → 公布(计票) → 备案归档 → 复审子通道 | full | 制度/规范/标准 |

**阶段附注**：PLA 批准须过衔接硬闸门（下位服从上位、专项服从总体）。STR 内圈审议产出**三形态裁定**（原则通过／退回修改附意见清单／暂不讨论，以 `ruling` 锚点登记；无裁定不得进入终审），终审批准采**一致同意**（现实原型：常委会合议一致，ADR-0003）。LEG 合议审议同为三形态且不计票，计票在公布批准环节。**一般原理（ADR-0003）：意见生产分布式、收敛单点化**——每个案卷只设一个收敛点，其余环节皆为意见生产；收敛点的通过规则依被模拟机构的现实惯例（见 §4 表）。

## 2. 双维度配置

人数（complexity）：simple=cppcc 2+npc 1；medium=3+2；complex=4+3；enterprise=5+5。

验收门（validation）：full＝每次 R4 后暂停请示＋终批启用特殊通过线；key＝仅关键阶段后暂停；skip＝全程自主。PLA 另按年度评价（过程性）/五年考核（终局性）双层节奏；数据造假直接不合格。

## 3. 建会（P 阶段）

P1 议题包：`team_note` key=`agenda-{案卷号}`（**会议作用域键**）：议题一句话（注明来源类别：用户指定／调研发现／成员动议，遵循小切口原则）、背景与期望结果、成功标准（编号列表，规划型标注约束性/预期性属性）、约束、类型代号与阶段表、三分时点（会前送达/会中讨论/会后报送时限）。

**案卷号**（旧称文号）按 `research/C-补-P12` 代字规则：`PC-{类型字}〔年份〕{序号}号`。它是**一个议题的完整档案编号**，不是会议的编号——「多事一会」的现实做法＝团队不解散，连续召开多个单议题案卷（逐项审议、逐项决定），会后由主持人**合成总纪要**分条引用各案卷决议（国常会模式，ADR-0001）。

P2 组队（全部 `relation: managed`）：cppcc-i 绑定 §6 提案视角 persona；npc-j 绑定刚性审查定位 persona。persona 模板强制行为规约：

`你是{身份名}，专长{领域}。规约：只回应主持人点名的问题；结论先行，观点必须给理由；意见书≤300字、质询≤100字、选票理由≤80字（字限为行为规约，超限记档不改变效力判定）；禁止纯程序性发言与寒暄；允许对他方观点质疑交锋，由主持人裁判；对程序疑问用询问通道（≤50字短问）；产物以 team_note 写入指定 key 后 team_send 通知主持人一句。`

P3 任务板：每个大流程阶段建 `team_task`；当前置 active，完成置 done 并把决议要点写进 note（一文一事）。

## 4. 协商回路（⭐阶段的执行单元；同一议题总轮次≤3）

### R0 出题（主持人）
`team_note` key=`issue-{案卷号}-{stageid}`：背景输入、要回答的问题、《意见书》格式与准入标准、产出时限。然后 `team_send` 点名全体 cppcc。

### R1 独立陈述（cppcc）
各成员把《意见书》写入 `opinion-{案卷号}-{stageid}-{name}` 并通知主持人。主持人结束回合等待投递唤醒（回合驱动屏障，仅限常驻会话；单发环境见运行形态前提）。

**准入审查（M4，先于转录上板）**：①一事一案；②有情况、有分析、有具体建议；③重复者并案标注；④超出议题范围者转出另立；⑤超字数上限者退回重提。不合格的**退回修改重提**（附理由），原稿留痕不删除，不得静默丢弃。
收集判定：全员到齐进 R2；超时追点一次；仍缺且已收 ≥2/3 继续（缺席记档），<2/3 报告用户请示。

### R2 交叉质询与询问（npc ⇄ cppcc）
主持人汇总意见书写入 `issue-{案卷号}-{stageid}-digest`，点名全体 npc 各提至少 1 个书面质询（`inquiry-{案卷号}-{stageid}-{name}`），可要求限期答复。质询转发相关 cppcc，**限 1 回合内答辩**（`reply-{案卷号}-{stageid}-{name}`，≤100 字为插件补充规约），超时催办一次；提案方不满意可触发一次二次答辩。未被点名的成员无答辩义务。
**询问通道（M17）**：任何成员可随时向主持人发 ≤50 字短问，不占质询名额、不进计票程序。

### R3 合议修订（主持人主导）
综合意见书、质询、答辩形成《草案 v2》写入 `draft-{案卷号}-{stageid}`。**双联交付**：修订文本＋《意见处置清单》成对产出——逐条记录来源、经研究摘要、处置结果四分类（采纳/部分采纳/存疑留办/不采纳）及理由，全部处置完毕方可定稿。实质性修改后回传原提案方一轮快确认。主持人保持中立合议，不表态站队、不参与表决（M11）。

### R4 收敛（npc；收敛形式依被模拟机构惯例，ADR-0003）

**启动门槛**：npc 应答率 ≥2/3 方可付表决；simple 档仅 1 名 npc 时必须应答。不足⇒计票降级**征询模式**：该轮**不构成表决**（协议自定语义——现实制度仅设启动门槛、不足即不开会且无事后救济明文，见调研 A-补-P05；ADR-0004），主持人须将征询结果呈报用户三选：①采信＝登记决议并强制标注「征询采信·未达法定状态」后走完阶段收尾归档；②再议＝提炼缺席与分歧要点回 R1 重议一轮；③终止＝搁置归档附原因。三选在 skip/key 验收档下同样强制请示——征询模式的本质即人类裁量。
立场提交：《选票/确证书》写入 `vote-{案卷号}-{stageid}-{name}`，一人一票不可更改。

**通过规则表**：

| 收敛点 | 规则 | 机械判定 |
|---|---|---|
| MIN 确认 | certify（ADR-0002） | 无更正 且 应答率达标 ⇒ 纪要确证 |
| CON/RES 审议 | majority | 赞成 × 2 > 编制（弃权计入分母＝算术反对） |
| PLA 批准 | majority | 同上（现实：规划纲要由人大过半数表决） |
| STR 终审 | unanimous | 赞成 ＝ 编制（一致同意，一票即阻；现实原型：常委会合议一致） |
| LEG 公布 | two-thirds | 赞成 × 3 ≥ 编制 × 2 |

**失败分支**：MIN＝存在更正 → 主持人修订记录后重新发起确证（**更正循环 ≤3，纠错上限语义，非三审制**；应答率不足则阻止归档——确证不完整即一无所有）；其余类型＝法定表决未通过时提取反对焦点写入 `issue-{案卷号}-{stageid}-focus` 回 R1 重议（同一议题总轮次 ≤3）。搁置跨两个会议周期未推进 → 自动归档终止。结果写入 `resolution-{案卷号}-{stageid}`（票数明细＋每位代表理由＋成文日期=R4 通过日）。

### 验收门
按 §2 validation 在 R4 后决定是否暂停请示。展示：阶段名、决议、票数、异议要点、下一步计划。

**用户批复＝程序性三选（ADR-0005）**：①放行——登记 resolution 后走收尾归档；②附意见打回——用户实质意见由主持人转写为焦点（`issue-{案卷号}-{stageid}-focus`）回 R1 重议（消耗轮次）；③终止——搁置终止附原因。用户实质修改意见**不得直写进决议文本**，一律经协商回路落实后表决；批复不构成票、不改变通过规则。与征询呈报三选同源的一般原理（ADR-0004/0005）：**人类裁量只产生程序性处置，实质内容必经协商回路与表决**。

### 监督窗口（用户介入通道，ADR-0006）

会中用户＝民众监督者：可在**任意 ⭐ 阶段**提出监督质疑（各征意阶段为主窗；现实锚点：立法法§40 窗口开于常委会会议后、表决前关闭），**计票启动即关窗**；归档后的质疑改走复审子通道（同构备案审查公民建议）。入板＝主持人**代录** `opinion-{案卷号}-{stageid}-用户`（或 inquiry）标注「代录·用户」：**原汁原味不改写原文**（基层立法联系点纪律）、照过 M4 准入但不因批评性被拒、不替代成员产物的前置门计数（STR 终审阶段加标「参考输入·非表决性」）。效力边界：监督意见＝**输入非裁决**（现实原句「本次征集的只是提案线索而不是政协提案」）——经质询答复、《处置清单》逐条处置、必要时打回重议、表决落文；用户不因此获得投票权。反馈义务分层：基础档＝全量收集整理＋征求情况向全员通报（立法法§41/§40③ 同构）；逐条回告用户属协议强化语义（现实为记者会点名通报/邀请线索人参加督办的实务形态）。

## 5. MIN 记载程序与确证书（ADR-0002）

MIN 不开 R0-R4——它是**记载性程序**（条例第八条：纪要「记载」议定事项；议定在先，纪要在后，不产生新决定）：
①情况介绍（主持人写议题卡）→ ②预约式发言（每人 1 次 ≤300 字；即席补充每人限一次 ≤200 字）→ ③归纳确认：主持人合成纪要稿宣布，成员经 pc_vote 提交**确证书**——`确认`（记录如实）或 `更正：<失真处>`（≤80 字），**无需意见书与质询前置**。
机械保证：无更正且应答率达标 ⇒ 确证生效，可归档；出现更正 ⇒ 修订记录重新确证（更正循环 ≤3）；应答率不足 ⇒ 阻止归档。窗口封闭后纪要即成执行依据（现实条款：与会单位事后不得拒绝落实会议精神）。涉对立立场议题时，预约名额强制分配给不同立场成员。

## 6. 身份库

npc 审查视角（每场至少覆盖可行性 + 风险/合规；定位=刚性审查）：npc-feasible 可行性评估师 / npc-risk 风险评估师 / npc-compliance 合规审计员 / npc-quality 质量监督员 / npc-perf 性能评估师 / npc-global 全局一致性代表。

cppcc 提案视角（按议题领域挑 2-5 个互补专业；定位=协商式监督与参政议政）：
架构/技术：系统架构师、软件架构师、数据架构师、AI 工程专家｜产品/商业：产品策略师、增长专家、商业模式分析师、用户研究员｜工程/交付：DevOps 专家、后端专家、前端专家、测试专家、项目经理｜数据/安全：数据分析师、安全工程师、隐私合规师｜运营/成本：运营专家、成本控制师、供应链专家、法务顾问｜内容/市场：内容策略师、市场分析师。

选题启发：议题关键词命中领域 → 该领域至少 1 名 cppcc + 对应审查视角 npc 必在场。

## 7. 文档生成

元信息块：案卷号、类型、议题、复杂度、参会名单（列身份名）、成文日期（=最终通过日）、验收模式。骨架按各类型章节执行（MINUTES 含批示回流占位；CONSULTATION 附录含处置清单；PLANNING 含指标分解单与预审意见；LEGISLATIVE 含备案登记）。规则：内容一律取自板书与档案结构化记录（插件形态用 pc_inspect 取全文），禁止编造；附录列全部键索引；重大事项决议以公告体发布。文档写入工作区 `.pandaclaw/{案卷号}.md`。公文版式参数见仓库 `templates/layout-gbt9704.yaml`（GB/T 9704 红头版式）。

## 8. 红线

1. 成员一律 managed；出现横向消息立即纠正并记档。
2. **表决前置门＋全链顺序**：`vote-*` 前必须已存在同 stage 的 `opinion-*` 与 `inquiry-*`（**MIN 确证书豁免质询**；紧随裁定门的终审由上游审议蒸馏满足）；最小文书序列（议程→意见→质询→答辩→草案→选票→决议）构成合法迁移链，跳步即程序违规。
3. 计票只认 `vote-*` 板书【投票】行；聊天散句不算票；字数超限记档但不影响选票效力。
4. 成员不得自行宣布结论；结论只能出自主持人归档的 `resolution-*`。用户的验收门批复同理——仅产生程序性处置，实质意见须回协商回路（ADR-0005）。
5. 一事一案、一文一事——「事」指议题（裁决单元），一场会议可容纳多个议题（各自立案卷，见 §3）。
6. 全程不删除板书（审计链）；错误记录用新 key 覆盖并注明。
7. 主持人在合议与表决中保持中立，不提案、不投票。
8. 解散团队前必须完成文档生成与存档。
